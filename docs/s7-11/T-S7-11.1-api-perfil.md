# T-S7-11.1 — API segura de perfil y edición (#336)

## Alcance y auditoría previa

La revisión de `origin/develop` en `be56e8d14d3701728b7376245a569e738dbfb29c`
encontró:

- `GET /api/auth/me`, autenticado, que devuelve `id`, `email`, `rol`,
  `tipo_cliente`, `nombre`, `estadoAprobacionEmpresa` y
  `cuentaCorrienteHabilitada`, sin datos de contacto ni edición.
- `GET /api/admin/clientes`, exclusivo ADMIN, para listado administrativo.
- Persistencia de `CLIENTE` y `USUARIO` mediante TypeORM, con el esquema SQL como
  autoridad y sin migraciones automáticas.
- Registro público con `nombreRazonSocial`, `email`, `password`, `docCliente`,
  `cuit`, `telefono` y `direccion`.

No existía una API para que un cliente consultara o editara su propio perfil.
`/api/auth/me` se conserva sin cambios para no alterar el contrato consumido por
el frontend y por las pruebas de restauración de sesión.

La tarea #336 de Taiga no fue accesible sin credenciales: la API externa
responde `401 Authentication credentials were not provided` y la interfaz es una
SPA privada. Este documento registra el contrato implementado con los criterios
disponibles en el repositorio y las restricciones explícitas del pedido. No se
amplió el alcance a credenciales, datos fiscales ni estados administrativos.

## Contrato

### `GET /api/perfil`

Requiere cookie `jwt_token` válida y rol `CLIENTE`. No acepta ni usa IDs de
cliente o usuario enviados por el cliente. Responde `200`:

```json
{
  "data": {
    "perfil": {
      "id": 12,
      "tipoCliente": "PARTICULAR",
      "nombreRazonSocial": "Cliente de prueba",
      "email": "cliente@example.test",
      "docCliente": "30111222",
      "cuit": null,
      "telefono": "294 400 0000",
      "direccion": "Calle 1",
      "estadoAprobacionEmpresa": null,
      "cuentaCorrienteHabilitada": null
    }
  }
}
```

- `id` es `USUARIO.id_usuario` de la sesión y es solo informativo.
- `tipoCliente` es `PARTICULAR` o `EMPRESA`.
- `estadoAprobacionEmpresa` y `cuentaCorrienteHabilitada` son de solo lectura;
  para `PARTICULAR` valen `null`.
- No se devuelven `password_hash`, tokens, flags internos, listas de precio,
  límites de crédito ni datos de otros clientes.

### `PATCH /api/perfil`

Requiere la misma sesión. El body admite únicamente:

| Campo | Tipo | Límite | Limpiar |
| --- | --- | --- | --- |
| `telefono` | texto | 50 caracteres Unicode | `null` |
| `direccion` | texto | 500 caracteres Unicode | `null` |

Debe enviarse al menos uno. Los textos se recortan en los extremos; un texto
vacío o solo espacios se rechaza. Los campos omitidos conservan su valor. No se
aceptan `id`, `id_cliente`, `email`, `password`, `rol`, `tipo_cliente`,
`nombreRazonSocial`, `docCliente`, `cuit`, `estadoAprobacionEmpresa`,
`cuentaCorrienteHabilitada`, `activo`, `es_fiel`, listas de precio ni límites de
crédito.

```json
{
  "message": "Perfil actualizado correctamente.",
  "data": { "perfil": { "...": "contrato completo de GET" } }
}
```

## Errores

| HTTP | Situación | Respuesta |
| --- | --- | --- |
| 400 | Body ausente, no objeto, vacío, campo desconocido, valor inválido, JSON malformado o primitivo JSON | `{ "message": "..." }` |
| 401 | Cookie ausente, inválida o expirada; usuario inactivo o inexistente, incluso si se desactiva dentro de la transacción | `{ "message": "No autenticado." }` |
| 403 | Sesión válida con rol ADMIN; en `PATCH`, cliente inactivo o vínculo/rol inválido revalidado bajo lock | `{ "message": "..." }` |
| 404 | El usuario CLIENTE autenticado no tiene fila de perfil activa asociada | `{ "message": "Perfil no encontrado." }` |
| 413 | El cuerpo excede el límite del lector JSON | `{ "message": "..." }` |
| 500 | Error de base o resultado incierto | Mensaje genérico o el mensaje seguro de resultado desconocido |

Las respuestas de perfil usan `Cache-Control: private, no-store` y `Vary: Cookie`,
incluidos los errores del lector JSON. El router de perfil instala su propio
`express.json()` antes del parser global para conservar `{ message }` y las
cabeceras privadas ante JSON malformado, primitivos o payload excesivo.
Los logs no incluyen payloads, contraseñas, tokens ni errores del driver.

## Seguridad

- **IDOR:** la ruta no tiene `:id`; el repositorio recibe únicamente
  `req.auth.id` y resuelve `CLIENTE` mediante `USUARIO.id_cliente`.
- **Mass assignment:** el DTO usa lista blanca estricta y `forbidNonWhitelisted`.
  Cualquier campo no autorizado produce `400` antes de llegar al servicio.
- **Sesión:** Passport JWT valida firma, algoritmo, expiración, usuario activo y
  rol persistido en cada solicitud. La identidad no se toma del body ni del query.
- **Persistencia:** las lecturas filtran `USUARIO.activo = 1`,
  `CLIENTE.activo = 1` y `rol = CLIENTE`. La edición localiza `id_cliente` sin
  lock, bloquea primero `CLIENTE`, después `USUARIO`, y revalida bajo ambos
  bloqueos la titularidad, el rol y los dos estados activos antes de escribir.
  La lectura de respuesta ocurre dentro de la misma transacción. Un fallo
  posterior a la escritura revierte todo.
- **Concurrencia:** el orden `CLIENTE → USUARIO` es el global de carrito,
  checkout y crédito, y evita el ciclo AB-BA con esos flujos. Dos PATCH
  simultáneos sobre campos distintos conservan ambos; sobre el mismo campo, la
  última escritura confirmada gana sin estados parciales.
- **DTO:** además de las longitudes y el recorte vigentes, se rechazan NUL, los
  controles C0 no blancos, DEL y los controles C1. Se conservan tabulación, LF y
  CR para direcciones multilínea legítimas y no se restringen acentos, `°`, `#`,
  `/`, `—` ni otros símbolos habituales.

## Campos no editables y justificación

`email` y `password` son credenciales y requieren un flujo específico que #336 no
define. `cuit`, `docCliente` y `nombreRazonSocial` son datos de identidad fiscal
o legal. `estadoAprobacionEmpresa`, la habilitación de cuenta corriente y los
límites de crédito son estados administrativos y comerciales. Ninguno se puede
modificar desde esta API.

## Correcciones de auditoría #336

Las reproducciones adversariales se ejecutaron sobre MariaDB 11.4 descartable
antes y después de la corrección:

| Hallazgo | Causa reproducida | Corrección |
| --- | --- | --- |
| H-01 P1 | `GET` devolvía `200` con `CLIENTE.activo = 0`; `PATCH` actualizaba un cliente inactivo y podía persistir si `USUARIO.activo` cambiaba entre Passport y el `UPDATE`. | Filtro de ambos estados en lecturas, localización sin lock y revalidación de identidad, vínculo, rol y actividad bajo `CLIENTE → USUARIO`. |
| H-02 P1 | El perfil tomaba `USUARIO → CLIENTE` mientras carrito/checkout/crédito toman `CLIENTE → USUARIO`; una prueba concurrente real produjo `ER_LOCK_DEADLOCK` 1213. | Se alineó el orden global `CLIENTE → USUARIO`; la prueba de regresión verifica que perfil y carrito se serializan sin deadlock ni pérdida de la actualización. |
| H-03 P2 | El parser global respondía `400 { "error": "Solicitud inválida" }` sin cabeceras privadas ante JSON malformado o primitivo. | Parser y manejador propios de `/api/perfil` antes del parser global, con `{ message }`, `Cache-Control: private, no-store`, `Vary: Cookie` y `413` para exceso de tamaño. |
| H-04 P3 | El DTO aceptaba `\u0000` y otros controles. | Rechazo de NUL, controles C0 no blancos, DEL y C1; se conservan tabulación, LF, CR y formatos legítimos. `updatePerfilPolicy` se incorporó a `test:dto-source`. |
