# T-S7-05.2 — Verificación de precios posterior al alta o edición

> Estado: implementación local sujeta a revisión técnica de Lucci.
> Rama: `feature/s7-05-2-price-verification-workflow`.
> Base: `develop` vigente al 15/11/2026. T-S7-05.1 no estaba integrada en
> `develop` al iniciar esta tarea; este documento no depende de su carpeta
> `docs/s7-05/README.md`.

## 1. Problema y alcance

El motor FER17-v1 ya calculaba precios y bloqueaba bases sin evidencia. Faltaba
un procedimiento operativo para que un ADMIN revisara manualmente un importe
nuevo o editado y registrara evidencia comercial real sin abrir un endpoint HTTP
de escritura de evidencias.

Esta tarea agrega:

- un servicio transaccional reutilizable de verificación;
- un comando local autorizado (`npm run precio:verificar`);
- un historial append-only de eventos de precio;
- la invalidación automática de evidencia cuando cambia `PRODUCTO.precio`;
- pruebas de integración MariaDB y documentación operativa.

No cambia la aritmética FER17-v1 ni relaja sus validaciones. Una base positiva sin
evidencia vigente sigue sin publicarse como importe USD comprable.

## 2. Arquitectura elegida

### Por qué no un endpoint HTTP

La operación FER-17 vigente exige que la carga de evidencia use una credencial
operativa separada y que esas escrituras no se expongan por HTTP. Para respetar
ese contrato:

1. La verificación se ejecuta con un comando local que usa la credencial
   operativa de base de datos.
2. No se agregó ninguna ruta HTTP para crear, editar o invalidar evidencias.
3. La edición administrativa de precio sigue usando el endpoint existente, pero
   la invalidación de evidencia y la auditoría las ejecuta un trigger de MariaDB
   con privilegios de definidor, no el código HTTP con credenciales de cliente.
4. El actor se transmite al trigger mediante una variable de sesión interna,
   `@fer17_actor_id`, fijada por el backend en su propia conexión transaccional.
   El trigger vuelve a comprobar que ese id sea un `ADMIN` activo.

### Componentes

| Componente | Responsabilidad |
| --- | --- |
| `backend/src/services/pricing/price-verification.rules.ts` | Validación pura de importe, evidencia e identificadores. |
| `backend/src/services/pricing/price-verification.ts` | Transacción de verificación, rechazo auditado, consulta de historial y comprobación FER17 posterior al COMMIT. |
| `backend/scripts/verify-product-price.cjs` | Procedimiento administrativo local, sin HTTP. |
| `FER17_PRECIO_EVENTO` | Historial append-only de alta, cambio, verificación, invalidación y rechazo. |
| `fer17_producto_alta_evento` | Registra `ALTA` al insertar un producto. |
| `fer17_producto_precio_evento` | Al cambiar el precio, invalida evidencia y registra `CAMBIO_PRECIO` e `INVALIDACION` en la misma transacción. |

### Modelo de la evidencia

`PRECIO_USD_EVIDENCIA` conserva una fila por producto con el último importe
revisado. FER17 solo la acepta si `valida=1`, `precio_verificado=PRODUCTO.precio`
y `verificado_utc<=fecha de uso`.

`FER17_PRECIO_EVENTO` conserva el historial que la fila única no puede conservar.
No tiene FK a `PRODUCTO` ni a `USUARIO` de forma intencional: la auditoría debe
sobrevivir a mantenimientos de catálogo/usuarios y no se puede borrar en cascada.
La aplicación valida ambos identificadores antes de escribir.

## 3. Quién puede verificar

Puede verificar únicamente un operador que:

1. tenga acceso a la credencial operativa local del backend;
2. indique un `id_usuario` que exista en `USUARIO`;
3. tenga `rol='ADMIN'`;
4. esté `activo=1` en el momento de la transacción;
5. confirme explícitamente la revisión con `--confirmar`.

El servicio bloquea la fila del ADMIN con `SELECT ... FOR UPDATE`, por lo que una
desactivación concurrente no puede completarse mientras la verificación está en
curso.

Un `CLIENTE`, un visitante, un ADMIN inexistente o un ADMIN inactivo no pueden
figurar como verificadores. El id no se acepta desde una petición HTTP: no existe
tal endpoint. La autorización real es la combinación de acceso a la credencial
operativa y la fila ADMIN activa validada en servidor.

## 4. Evidencia comercial aceptable

El software no puede comprobar por sí mismo la autenticidad de un documento
externo. Lo que sí exige es una referencia concreta y reproducible que el
operador revisó manualmente.

Se aceptan, por ejemplo:

- factura o presupuesto del proveedor con número, fecha y origen;
- lista de precios oficial con vigencia y publicación;
- orden de compra firmada o documento equivalente;
- publicación archivada identificable por URL/fecha;
- acta o constancia interna con identificador único.

La referencia debe tener entre 8 y 1000 caracteres e incluir documento, origen o
localizador. Se rechazan:

- vacío, espacios o solo signos;
- textos genéricos como `ok`, `test`, `verificado`, `factura`, `n/a`;
- referencias que declaren `SINTETICO`, `DEMO`, `FIXTURE`, `MOCK` o equivalentes;
- caracteres de control.

Registrar una referencia no demuestra que el documento sea auténtico. La
responsabilidad de la revisión manual queda en el ADMIN identificado y en la
evidencia aportada.

## 5. Flujo A — Alta de producto

1. Un ADMIN crea el producto por el endpoint administrativo existente.
2. `PRODUCTO.precio` se guarda con el valor exacto normalizado a dos decimales.
3. El trigger registra `ALTA` en `FER17_PRECIO_EVENTO` con el ADMIN autenticado.
4. No se crea evidencia comercial automáticamente.
5. `/api/precios` devuelve `estadoPrecio: "BASE_NO_VERIFICADA"`, importes nulos y
   `precioComprable: false` hasta que exista revisión.

La importación administrativa también crea productos sin evidencia. Cuando la
confirmación conoce al ADMIN autenticado, el `ALTA` queda asociado a ese actor.

## 6. Flujo B — Verificar un precio nuevo o editado

Desde `backend/`, con `npm run build` ya ejecutado:

```bash
npm run precio:verificar -- \
  --producto 701 \
  --importe 100.00 \
  --evidencia "Factura A-0001-00000123 del proveedor Andes SA, revisada 15/11/2026" \
  --admin 999 \
  --confirmar
```

Secuencia transaccional:

1. valida importe y referencia antes de tocar la base;
2. abre transacción;
3. bloquea y revalida el ADMIN activo;
4. bloquea el producto con `SELECT ... FOR UPDATE`;
5. compara el importe esperado con `PRODUCTO.precio` como decimal exacto;
6. si no coincide, registra un `RECHAZO` y no modifica la evidencia;
7. si coincide, hace upsert de `PRECIO_USD_EVIDENCIA` con
   `valida=1`, `sintetica=0`, actor y `UTC_TIMESTAMP(3)` de MariaDB;
8. registra `VERIFICACION` en el historial;
9. confirma la transacción;
10. después del COMMIT consulta FER17 y espera `DEFINIDO` para un producto activo.

Salida esperada:

```text
Verificación registrada para el producto 701.
  Importe revisado: 100.00 USD
  Operador ADMIN: 999 <admin@example.test>
  Verificado UTC: 2026-11-15T18:00:00.000Z
  Evidencia: Factura A-0001-00000123 del proveedor Andes SA, revisada 15/11/2026
  FER17-v1: DEFINIDO
  Evento de auditoría: 42
```

Si el producto está inactivo o deja de ser visible, la evidencia puede quedar
registrada pero FER17 no publicará `DEFINIDO`; el comando informa la advertencia.

### Concurrencia

Si otra transacción cambió el precio antes de obtener el bloqueo, la verificación
relee el precio nuevo y rechaza el importe revisado anterior. No se registra
evidencia incorrecta. Dos verificaciones simultáneas del mismo importe se
serializan por el bloqueo del ADMIN/producto y dejan una sola fila de evidencia.

## 7. Flujo C — Editar el precio

El endpoint administrativo `PUT /api/admin/productos/:id` sigue siendo el único
camino HTTP de edición. Al cambiar `precio`, el trigger:

1. detecta que el importe cambió con comparación decimal (`<=>`);
2. lee la evidencia vigente;
3. la marca `valida=0` en la misma transacción;
4. registra `CAMBIO_PRECIO` con importe anterior/nuevo y actor;
5. registra `INVALIDACION` con la referencia invalidada.

Cambiar solo nombre, descripción, stock, imagen, categoría o estado activo no
invalida la evidencia.

### Caso obligatorio: 100 → 120 → 100

- USD 100 verificado: evidencia `valida=1`.
- Edición a USD 120: evidencia anterior `valida=0`, eventos `CAMBIO_PRECIO` e
  `INVALIDACION`.
- Edición de vuelta a USD 100: el trigger no rehabilita la fila; sigue
  `valida=0`.
- FER17 sigue en `BASE_NO_VERIFICADA` hasta una revisión nueva con evidencia
  nueva.

Nunca se copia ni se reutiliza automáticamente una evidencia anterior.

## 8. Flujo D — Rechazo o invalidación

Se rechaza con error explícito cuando:

| Código | Situación | ¿Registra evento? |
| --- | --- | --- |
| `EVIDENCIA_INVALIDA` | vacía, genérica, demasiado corta o con controles | No, es una entrada inválida antes de revisar un producto |
| `EVIDENCIA_SINTETICA` | referencia marcada como sintética/demo | No |
| `IMPORTE_INVALIDO` | importe no exacto, negativo o fuera de rango | No |
| `CONFIRMACION_REQUERIDA` | falta `--confirmar` | No |
| `ACTOR_NO_AUTORIZADO` | ADMIN inexistente, inactivo o rol incorrecto | No, no hay actor válido al que asociar |
| `PRODUCTO_INEXISTENTE` | id de producto inexistente | No |
| `PRECIO_AUSENTE` | producto sin precio | Sí, `RECHAZO` |
| `IMPORTE_NO_COINCIDE` | precio actual distinto del revisado | Sí, `RECHAZO` |

Un rechazo auditado no altera la evidencia vigente ni otros datos del producto.

## 9. Historial y auditoría

Consultar el historial por producto:

```bash
npm run precio:historial -- --producto 701 --limite 50
npm run precio:historial -- --producto 701 --json
```

Campos disponibles: producto, tipo, importe anterior/nuevo, evidencia,
evidencia anterior, ADMIN y email (si existe), instante UTC, resultado y motivo.

Tipos de evento:

- `ALTA`: creación del producto;
- `CAMBIO_PRECIO`: modificación real de `PRODUCTO.precio`;
- `VERIFICACION`: revisión manual aprobada;
- `INVALIDACION`: evidencia dejada sin efecto por cambio de precio;
- `RECHAZO`: intento de verificación rechazado con actor/producto válidos.

El historial es append-only a nivel de aplicación y permisos. No se exponen
endpoints HTTP para editarlo o borrarlo. No conceder `UPDATE` ni `DELETE` sobre
`FER17_PRECIO_EVENTO` a la aplicación.

## 12. Migraciones y despliegue

### Base nueva

Orden:

1. `database/schema.sql` — 22 tablas base, incluida `FER17_PRECIO_EVENTO`;
2. `database/migrate-fer-20-account-movements.sql` — 3 triggers FER-20;
3. `database/migrate-fer-17-price-verification.sql` — cuatro triggers FER-17 de alta, cambio de precio e inmutabilidad;
4. `seed.sql` / `verify-seed.sql` solo en desarrollo.

Resultado esperado: **22 tablas** y **7 triggers** (3 FER-20 + 4 FER-17).

### Base existente

Aplicar `database/migrate-fer-17-price-verification.sql` con escritores detenidos
y respaldo verificado. Es aditiva e idempotente:

- `CREATE TABLE IF NOT EXISTS FER17_PRECIO_EVENTO`;
- `CREATE OR REPLACE TRIGGER` para los cuatro triggers FER-17.

No convierte precios, no crea evidencia, no borra datos y no modifica
`PRECIO_USD_EVIDENCIA`. Reejecutarla no duplica triggers ni eventos.

### Rollback de código

Conservar la tabla y los triggers. Un rollback de código no debe borrar
auditoría. Si se necesita desplegar código anterior, la tabla y los triggers
pueden permanecer porque son compatibles con el esquema previo; no ejecutar
`DROP TABLE` ni `DROP TRIGGER` como parte de un rollback normal.

### Permisos

- Credencial operativa de verificación: `SELECT` en catálogo/usuarios,
  `SELECT`/`INSERT`/`UPDATE` en `PRECIO_USD_EVIDENCIA` y `SELECT`/`INSERT` en
  `FER17_PRECIO_EVENTO`.
- Usuario de aplicación HTTP: no necesita `UPDATE` sobre
  `PRECIO_USD_EVIDENCIA`; el trigger lo hace con privilegios de definidor.
- No conceder `UPDATE`/`DELETE` sobre `FER17_PRECIO_EVENTO` a la aplicación.
- El usuario que crea los triggers debe tener privilegios para actualizar
  evidencias e insertar auditoría, porque el trigger se ejecuta como definidor.

### Inventario parcial FER-20

Las pruebas y utilidades que solo instalan FER-20 siguen comprobando sus tres
triggers. Eso no certifica la instalación completa de los siete triggers.

## 13. Límites de seguridad

- No hay endpoint HTTP para verificar precios.
- El id de ADMIN no se confía por parámetro de cliente; se revalida en la
  transacción contra `USUARIO` activo y rol `ADMIN`.
- El importe se compara como decimal exacto; no se usa `Number`/`parseFloat` para
  dinero.
- El precio se bloquea con `FOR UPDATE`; un cambio concurrente impide aprobar un
  importe obsoleto.
- La invalidación de evidencia y la auditoría ocurren en la misma transacción que
  el cambio de precio.
- La evidencia sintética no se promociona automáticamente.
- Los errores del CLI no imprimen SQL, credenciales ni stacks.
- La evidencia no se escribe con credenciales de CLIENTE ni desde el navegador.
- La autenticidad documental no se verifica automáticamente; se exige revisión
  humana y referencia concreta.
