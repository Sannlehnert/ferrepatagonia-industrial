Respuestas conservadas: validación `{message}`; JSON malformado de auth `{message: 'Solicitud inválida.'}`, del resto `{error: 'Solicitud inválida'}`. 401/403 y cookies sin cambios. Existencia/categoría validada → 404, SKU/email UNIQUE → 409 conservados en servicios/DB; nunca validadores de unicidad. Errores de validación no incluyen valores, target, contraseña, token ni arrays ValidationError. Nuevos rechazos tienen mensajes fijos. Orden entre varios errores de entrada no forma parte de una garantía nueva.

Objetos/arrays en campos escalares se rechazan con mensaje fijo antes de `plainToInstance`, evitando recorridos de estructuras inesperadas. También se rechazan propiedades `__proto__`, `constructor`, símbolos y accesores antes de transformar: class-transformer omite algunas claves peligrosas y no se depende de esa omisión silenciosa. Los cuerpos JSON primitivos (incluido null) son rechazados primero por express.json con su envelope anterior. Cada política enumera sus campos; todas usan whitelist + forbidNonWhitelisted (productos/stock/login endurecen su tolerancia anterior). Los helpers síncronos antiguos siguen exportados para consumidores existentes, pero ejecutan los mismos DTO mediante validateSync; las rutas ejecutan validate asíncrono.

Pruebas previas inventariadas: auth.me/auth.middleware, register unit/HTTP + integración rollback/email concurrente, catalog unit/HTTP + integración snapshot/escape, adminProduct integración CRUD/stock/SKU/migración/precio fallback, orm y database-policy integración, categorías y clientes. Helpers de MariaDB crean contenedores nuevos sin volúmenes, puerto aleatorio loopback y BD UUID; no usar `.env` ni BD del proyecto. Frontend tiene test y build propios.

Dependencias: solo añadir class-validator 0.14.2 y class-transformer 0.5.1 (reflect-metadata ya existía); no actualizar dependencias ajenas de #212. #217 conserva middleware/JWT y recibe DTO Login ya conectado. No cambios de entidades, SQL, schema, frontend o Passport.

Decoradores: `experimentalDecorators:true`, `useDefineForClassFields:false` para conservar la ausencia de campos. No se necesita `emitDecoratorMetadata`: no se infieren tipos ni se usa @Type; la validación y el parseo son explícitos y el mismo flujo se prueba con tsx/esbuild y tsc/dist. reflect-metadata se carga desde el módulo de validación. Los DTO son clases separadas de las entidades; las interfaces de entrada del repositorio siguen siendo tipos internos, no validadores.
