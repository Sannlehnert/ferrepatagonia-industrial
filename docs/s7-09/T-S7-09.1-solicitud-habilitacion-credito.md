# T-S7-09.1 — Solicitud y habilitación de crédito comercial

Estado: implementación backend completa en la rama
`feature/s7-09-1-credit-workflow`. Pendiente de revisión técnica de Lucci y de
CI en GitHub Actions. No incluye interfaz gráfica.

## 1. Objetivo y alcance

Implementar el flujo backend para que una empresa:

1. solicite una línea de crédito comercial;
2. un ADMIN activo apruebe o rechace la solicitud;
3. un ADMIN habilite o deshabilite la cuenta corriente;
4. un ADMIN modifique el límite autorizado;
5. cada decisión quede auditada y sea respetada por las compras a cuenta
   corriente existentes.

No se reemplazan FER-19 ni FER-20. Se reutilizan:

- autenticación Passport/JWT y middlewares de rol;
- `CLIENTE.estado_aprobacion_empresa` para la aprobación empresarial;
- `CUENTA_CORRIENTE` como fuente de habilitación, límite, plazo y cobertura;
- `MOVIMIENTO_CUENTA_CORRIENTE` exclusivamente para cargos y abonos;
- `calcularEstadoCuenta` y las validaciones de `lockAccountOrderContext` para
  que una compra vea inmediatamente la habilitación y el límite.

## 2. Cuatro conceptos que no deben confundirse

| Concepto | Quién lo controla | Dónde vive | Qué permite |
| --- | --- | --- | --- |
| Aprobación empresarial | ADMIN sobre `CLIENTE` | `estado_aprobacion_empresa` | Ser empresa sujeta a crédito. No habilita cuenta ni crea límite. |
| Aprobación de solicitud | ADMIN sobre `SOLICITUD_CREDITO` | `SOLICITUD_CREDITO` y `EVENTO_CREDITO` | Autoriza un límite y un plazo. Crea la cuenta **inhabilitada** si no existía. |
| Habilitación de cuenta | ADMIN sobre `CUENTA_CORRIENTE` | `habilitada` | Permite que la cuenta participe en una compra. No modifica deuda ni historial. |
| Elegibilidad de compra | Checkout FER-20 | Cálculo transaccional | Exige empresa aprobada, cuenta habilitada, cobertura completa, plazo y límite. |

Una empresa puede estar APROBADA y no tener crédito. Una cuenta puede estar
habilitada y aun así no ser comprable si su cobertura o plazo no están
acreditados. Aprobar una solicitud no habilita la cuenta.

## 3. Estados y transiciones

### Solicitud

```text
PENDIENTE ── aprobar ──> APROBADA
    │
    └──── rechazar ────> RECHAZADA
```

- Solo se resuelve una solicitud `PENDIENTE`.
- Una solicitud `APROBADA` o `RECHAZADA` es inmutable.
- Una rechazada no se aprueba después: se requiere una nueva solicitud.
- La base impide más de una `PENDIENTE` por cliente mediante la columna
  generada `estado_pendiente_cliente` y su índice único.
- Una empresa `PENDIENTE`, `RECHAZADA` o inactiva puede presentar una solicitud,
  pero no puede aprobarla. La compra también queda bloqueada.

### Cuenta

```text
INHABILITADA ── habilitar ──> HABILITADA
      ^                          │
      └────── deshabilitar ──────┘
```

Deshabilitar no borra la cuenta ni sus pedidos, movimientos, pagos,
imputaciones o vencimientos. El cliente conserva la consulta de historial.
La habilitación exige acreditación comercial mínima:

- `moneda_limite = 'USD'`;
- `evidencia_limite` no vacía;
- límite decimal no negativo;
- `plazo_dias` 30 o 60 y `evidencia_plazo`;
- `cobertura = 'COMPLETA'`, `evidencia_cobertura` y `cobertura_desde_utc`
  no futura.

Por eso una empresa no obtiene crédito solo por pasar a APROBADA.

## 4. Persistencia

### `SOLICITUD_CREDITO`

Registra la solicitud y su estado actual:

- cliente y usuario solicitante reales;
- monto solicitado USD `DECIMAL(12,2)`;
- plazo solicitado 30/60;
- estado;
- clave de idempotencia;
- fecha UTC de solicitud;
- actor, fecha, límite, plazo, motivo y evidencia de la resolución;
- cuenta corriente creada o autorizada.

Restricciones destacadas:

- monto positivo y dentro de `DECIMAL(12,2)`;
- moneda USD;
- estados válidos;
- coherencia entre estado y campos de resolución;
- UUID v4 para la clave de idempotencia;
- FK a cliente, usuario solicitante, usuario resolutor y cuenta.

### `EVENTO_CREDITO`

Bitácora append-only. No se actualiza ni elimina desde la aplicación:

- solicitud, cliente y cuenta afectados;
- tipo de evento;
- actor y rol;
- clave de idempotencia;
- estado anterior y nuevo;
- límite anterior y nuevo;
- moneda;
- motivo y evidencia;
- revisión de cuenta;
- fecha UTC;
- resultado serializado de la operación.

Tipos:

- `SOLICITUD_CREADA`
- `SOLICITUD_APROBADA`
- `SOLICITUD_RECHAZADA`
- `CUENTA_HABILITADA`
- `CUENTA_DESHABILITADA`
- `LIMITE_MODIFICADO`

No se usa `MOVIMIENTO_CUENTA_CORRIENTE` para decisiones administrativas: una
decisión no es un cargo ni un abono y no debe alterar el saldo.

## 5. API

Todas las respuestas usan `{ "data": ... }`; los errores usan
`{ "message": "...", "code": "..." }` y, cuando corresponde, campos escalares
adicionales. Las rutas privadas responden
`Cache-Control: private, no-store` y `Vary: Cookie`.

Las escrituras exigen `Idempotency-Key: <UUID v4>`. La clave se normaliza a
minúsculas y queda vinculada al actor autenticado.

### CLIENTE

| Método | Ruta | Cuerpo | Resultado |
| --- | --- | --- | --- |
| `POST` | `/api/cuenta-corriente/solicitudes` | `montoSolicitado` string, `plazoDias` 30/60, `observaciones` opcional | 201 primera creación; 200 reintento idempotente |
| `GET` | `/api/cuenta-corriente/solicitudes?limite=&antesDeId=` | — | Solicitudes propias |
| `GET` | `/api/cuenta-corriente/solicitudes/:id` | — | Solicitud propia o 404 |

El cliente nunca envía `clienteId`, `usuarioId`, actor ADMIN, estado, límite,
saldo ni evidencia. El DTO rechaza campos desconocidos. El `clienteId` se
resuelve desde `USUARIO.id_usuario` autenticado y se revalida en la transacción.

Ejemplo:

```http
POST /api/cuenta-corriente/solicitudes
Idempotency-Key: 123e4567-e89b-42d3-a456-426614174000
Content-Type: application/json

{
  "montoSolicitado": "1500.00",
  "plazoDias": 30,
  "observaciones": "Compra de insumos"
}
```

```json
{
  "data": {
    "solicitud": {
      "id": 12,
      "estado": "PENDIENTE",
      "montoSolicitado": "1500.00",
      "plazoDias": 30,
      "moneda": "USD",
      "observaciones": "Compra de insumos",
      "fechaSolicitud": "2026-11-16T12:00:00.000000Z",
      "fechaResolucion": null,
      "limiteAutorizado": null,
      "plazoAutorizado": null
    }

```

### ADMIN — solicitudes

| Método | Ruta | Cuerpo | Resultado |
| --- | --- | --- | --- |
| `GET` | `/api/admin/solicitudes-credito?limite=&antesDeId=&estado=&clienteId=` | — | Listado |
| `GET` | `/api/admin/solicitudes-credito/:id` | — | Detalle |
| `POST` | `/api/admin/solicitudes-credito/:id/aprobar` | `limiteAutorizado`, `plazoDias`, `evidencia`, `motivo` | 200 |
| `POST` | `/api/admin/solicitudes-credito/:id/rechazar` | `motivo`, `evidencia` opcional | 200 |
| `GET` | `/api/admin/credito/eventos?limite=&antesDeId=&clienteId=&solicitudId=&tipo=` | — | Auditoría |

Ejemplo de aprobación:

```http
POST /api/admin/solicitudes-credito/12/aprobar
Idempotency-Key: 123e4567-e89b-42d3-a456-426614174001
Content-Type: application/json

{
  "limiteAutorizado": "2000.00",
  "plazoDias": 30,
  "evidencia": "ACTA-CREDITO-2026-001",
  "motivo": "Aprobación comercial"
}
```

La aprobación:

- exige ADMIN activo;
- exige `CLIENTE` activo, `EMPRESA` y `APROBADA`;
- exige al menos un usuario CLIENTE activo;
- crea la cuenta `INHABILITADA` si no existe, con cobertura de alta sin deuda
  previa, plazo y evidencia;
- si la cuenta ya existe, actualiza límite, plazo y evidencia bajo el mismo
  bloqueo que las compras;
- rechaza reducir el límite por debajo del crédito utilizado;
- no habilita la cuenta.

### ADMIN — cuenta

| Método | Ruta | Cuerpo | Resultado |
| --- | --- | --- | --- |
| `POST` | `/api/admin/clientes/:clienteId/cuenta-corriente/habilitar` | `evidencia`, `motivo` opcional | 200 |
| `POST` | `/api/admin/clientes/:clienteId/cuenta-corriente/deshabilitar` | `motivo`, `evidencia` opcional | 200 |
| `PUT` | `/api/admin/clientes/:clienteId/cuenta-corriente/limite` | `limite`, `evidencia`, `motivo` | 200 |

Ejemplo de límite:

```http
PUT /api/admin/clientes/7/cuenta-corriente/limite
Idempotency-Key: 123e4567-e89b-42d3-a456-426614174002
Content-Type: application/json

{
  "limite": "2500.00",
  "evidencia": "ACTA-LIMITE-2500",
  "motivo": "Ampliación comercial"
}
```

`limite` es una cadena decimal canónica, no negativa, con hasta dos decimales
y dentro de `DECIMAL(12,2)`. No se aceptan números JSON ni exponentes.

| 409 | `SOLICITUD_PENDIENTE` | Ya existe una solicitud pendiente |
| 409 | `SOLICITUD_NO_PENDIENTE` | La solicitud ya fue resuelta |
| 409 | `CLAVE_IDEMPOTENCIA_REUTILIZADA` | La clave se usó con otros datos |

| 409 | `CUENTA_NO_ACREDITADA` | Faltan requisitos comerciales |

## 6. Autorización

| Operación | CLIENTE | ADMIN activo | ADMIN inactivo/degradado |
| --- | --- | --- | --- |
| Crear solicitud propia | Sí, solo EMPRESA activa | No | No |
| Consultar solicitudes propias | Sí | No | No |
| Consultar solicitudes ajenas | 404 | Sí | No |
| Aprobar/rechazar | No | Sí | No |
| Habilitar/deshabilitar | No | Sí | No |
| Modificar límite | No | Sí | No |
| Consultar historial de cuenta | Sí, aunque esté deshabilitada | Sí | No |
| Comprar a crédito | Solo si FER-20 lo habilita | Fuera del flujo | No |

La identidad se deriva de Passport/JWT. Cada transacción vuelve a leer
`USUARIO.activo`, `USUARIO.rol`, `CLIENTE.activo` y la titularidad. No se
confía en `id_admin`, `clienteId`, estado, límite anterior ni permisos del body.

## 7. Transacciones, locks e idempotencia

Orden de adquisición:

1. `CUENTA_CORRIENTE FOR UPDATE` cuando la operación afecta la cuenta;
2. `CLIENTE FOR UPDATE`;
3. `USUARIO` actor `FOR UPDATE`;
4. `SOLICITUD_CREDITO FOR UPDATE`;
5. `EVENTO_CREDITO` por clave de idempotencia.

Las compras FER-20 ya bloquean la cuenta primero. Por eso:

- dos compras y un cambio de límite se serializan por cuenta;
- un cambio de límite durante una compra ve la deuda confirmada o la compra ve
  el límite nuevo, nunca un estado parcial;
- dos aprobaciones de la misma solicitud: una gana y la otra recibe
  `SOLICITUD_NO_PENDIENTE`;
- aprobación y rechazo concurrentes: solo una transición se confirma;
- dos habilitaciones o deshabilitaciones: una gana y la otra recibe 409;
- dos cambios de límite: se serializan y ambos quedan auditados.

Las operaciones son transaccionales. Si el COMMIT es incierto, la API devuelve
503 y no afirma una reversión. El cliente debe reintentar con la misma
`Idempotency-Key`. La clave única por actor impide duplicar el evento. Un
reintento secuencial devuelve el resultado original. Dos reintentos
simultáneos con la misma clave pueden recibir 409; el siguiente reintento lee
el evento confirmado y devuelve el resultado original.

La aprobación, la habilitación y el cambio de límite actualizan
`CUENTA_CORRIENTE`; el trigger `fer260_cuenta_revision` incrementa `revision` y
los cursores existentes detectan el cambio. No se alteran movimientos,
imputaciones, pagos ni vencimientos.

## 9. Auditoría

Para reconstruir una decisión, consultar:

```http
GET /api/admin/credito/eventos?clienteId=7
```

Cada evento permite responder:

- qué cliente, solicitud y cuenta se afectaron;
- quién decidió y con qué rol;
- qué estado había y cuál quedó;
- qué límite había y cuál quedó;
- cuándo ocurrió en UTC;
- qué motivo y evidencia se usaron;
- cuál era la revisión de cuenta;
- cuál fue el resultado devuelto.

El cliente no recibe evidencia interna, motivo de resolución ni actor
administrativo en sus solicitudes.

## 11. Procedimiento administrativo

1. El cliente EMPRESA activo crea la solicitud con monto y plazo.
2. Un ADMIN activo consulta la solicitud pendiente.
3. El ADMIN verifica empresa activa y aprobada, antecedentes y evidencia.
4. El ADMIN aprueba con límite, plazo, evidencia y motivo.
5. La cuenta queda creada o actualizada, pero **inhabilitada**.
6. El ADMIN habilita la cuenta con evidencia cuando la operatoria comercial
   está lista.
7. Las compras FER-20 revalidan empresa, usuario, habilitación, cobertura,
   plazo y límite en cada confirmación.
8. Para suspender compras nuevas, el ADMIN deshabilita la cuenta. El historial
   sigue disponible.
9. Para ampliar o reducir el límite, se usa el endpoint de límite con evidencia.
   La reducción por debajo de lo utilizado se rechaza.

## 12. Limitaciones y riesgos

- No hay UI ni endpoints para configurar cobertura o plazo de cuentas legadas.
  Una cuenta existente sin acreditación completa no puede habilitarse por esta
  API; debe regularizarse por el procedimiento administrativo de FER-19/20.
- La aprobación de una solicitud crea una cuenta nueva con cobertura de alta
  sin deuda previa. No se hace backfill de cuentas históricas.
- Cambiar el límite no reescribe compras anteriores ni vencimientos.
- Si el actor es degradado o desactivado después de emitido el JWT, Passport
  rechaza la sesión y el servicio vuelve a validar dentro de la transacción.
- La auditoría es append-only por diseño de aplicación; no se agregaron
  triggers de inmutabilidad para no modificar el conteo de triggers FER-20 ni
  la coordinación con T-S7-05.2.
- Los errores de lock o de clave duplicada se devuelven como 409; un COMMIT
  incierto se devuelve como 503 y exige reintento con la misma clave.
