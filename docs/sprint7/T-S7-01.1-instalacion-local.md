# Sprint 7 · Instalación local normal (T-S7-01.1)

Esta guía describe una instalación limpia y persistente de Ferrepatagonia
Industrial con **MariaDB 11.4, backend y frontend**, sin usar el lanzador
académico `backend/test/helpers/run-demo286-local.cjs` ni cargar el catálogo
DEMO de 904 SKU.

El objetivo es que cualquier integrante pueda preparar el proyecto desde una
copia limpia, inicializar una base vacía y verificar el funcionamiento normal
de los servicios. La carga del catálogo definitivo de 100 productos pertenece a
otra tarea del Sprint 7 y no se realiza aquí.

Las guías canónicas siguen siendo [Operación y liberación](../operaciones-release.md),
[Base de datos](../../database/README.md) y [Backend](../../backend/README.md).
Esta guía concentra el procedimiento mínimo del Sprint 7 y las advertencias de
persistencia que deben respetarse.

## 1. Requisitos

- **Git**.
- **Node.js 22.22.2 + npm 10.9.7** como referencia reproducida por CI.
  - `backend` declara `"node": ">=22"`.
  - `frontend` declara `"^22.18.0 || >=24.12.0"`.
  - Verificar con `node --version` y `npm --version`. No se recomienda usar una
    versión anterior a la referencia de CI.
- **Docker** con contenedores Linux y **Docker Compose v2**.
  - Verificar con `docker --version`, `docker compose version` y `docker info`.
  - En Windows, Docker Desktop debe estar iniciado y con integración WSL
    habilitada si se trabaja desde una distribución WSL.
- Puertos libres: **3307** (MariaDB), **3000** (API) y **5173** (Vite).

## 2. Obtener el código e instalar dependencias

Desde la raíz del repositorio:

```bash
git switch develop
git pull --ff-only origin develop
```

Instalar dependencias de ambos paquetes:

```bash
npm --prefix backend ci
npm --prefix frontend ci
```

No usar `npm install` para una instalación reproducible: `npm ci` respeta el
`package-lock.json` versionado.

## 3. Iniciar MariaDB

Desde la raíz, donde está `compose.yml`:

```bash
docker compose config
docker compose up -d --wait --wait-timeout 180 mariadb
docker compose ps
```

Condiciones esperadas:

- La imagen es `mariadb:11.4`.
- El contenedor informa `healthy`.
- El puerto local es `127.0.0.1:3307` y el puerto interno es `3306`.
- El volumen `ferrepatagonia-dev_mariadb_data` conserva `/var/lib/mysql`.
- No se levanta ningún contenedor `demo286-*`.
- Las credenciales son las públicas de desarrollo de `compose.yml`; no se
  deben reemplazar por credenciales reales.

Comprobar la conexión. El comando debe quedar en una sola línea tanto en Bash
como en PowerShell:

```bash
docker compose exec mariadb mariadb --default-character-set=utf8mb4 -uferrepatagonia -pferrepatagonia_dev_only ferrepatagonia_dev -e "SELECT DATABASE() AS base, VERSION() AS version;"
```

El resultado esperado es la base `ferrepatagonia_dev` y una versión
`11.4.x-MariaDB`. Si el contenedor queda `unhealthy`, revisar:

```bash
docker compose logs --tail=100 mariadb
```

## 4. Preparar `backend/.env`

Crear el archivo local a partir de la plantilla:

```bash
cp backend/.env.example backend/.env
```

En PowerShell:

```powershell
Copy-Item backend\.env.example backend\.env
```

Generar un `JWT_SECRET` aleatorio y colocarlo en `backend/.env`:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

No compartir la salida, no registrarla en informes y no versionar `.env`.
El archivo ya está excluido por `.gitignore`.

La configuración mínima debe quedar alineada con `compose.yml`:

```dotenv
PORT=3000
DB_HOST=127.0.0.1
DB_PORT=3307
DB_NAME=ferrepatagonia_dev
DB_USER=ferrepatagonia
DB_PASSWORD=ferrepatagonia_dev_only
JWT_SECRET=<valor-generado-localmente>
NODE_ENV=development
APP_PUBLIC_ORIGIN=http://localhost:5173
TRUSTED_PROXY_CIDRS=none
AUTH_RATE_STORE=memory
API_PROCESS_COUNT=1
```

Los valores restantes de `.env.example` son adecuados para desarrollo local.
Joi valida la configuración al arrancar y falla antes de abrir la base o el
puerto HTTP si falta `JWT_SECRET`, `NODE_ENV` o algún dato de conexión.

### 4.1 Almacenamiento persistente de fotos, comprobantes e importaciones

El backend arranca y `GET /api/health` puede responder HTTP 200 aunque las
rutas de almacenamiento no estén configuradas. Eso **no** habilita las
funciones de archivos: sin rutas válidas, la subida de fotos y las operaciones
con comprobantes responden HTTP **503** (la consulta de una foto no disponible
devuelve **404**), y el estado de las importaciones no sobrevive reinicios ni
limpiezas temporales.

| Variable | Contenido | Sin configuración válida |
|---|---|---|
| `PRODUCT_IMAGE_STORAGE_DIR` | Fotos de producto normalizadas (`.webp`) | La subida responde HTTP **503**; la consulta de una foto, **404**. |
| `RECEIPT_STORAGE_DIR` | Comprobantes de pago (privados) | Las operaciones con comprobantes responden HTTP **503**. |
| `IMPORT_STORAGE_DIR` | Estado de confirmación de importaciones (`.json`) | Si se omite, se usa un directorio temporal **no persistente**; si se define mal, responde HTTP **503** sin fallback silencioso. |

Requisitos que deben cumplirse (validación Joi, servicios y utilidad de
preparación de T-S7-01.2):

- Rutas **absolutas**, sin NUL ni espacios en los extremos.
- **Fuera del checkout de Git**. `RECEIPT_STORAGE_DIR` no puede contener el
  repositorio ni estar contenida en él.
- Deben **existir antes** de usarse: el backend no crea los directorios.
- `PRODUCT_IMAGE_STORAGE_DIR` y `RECEIPT_STORAGE_DIR` deben ser directorios
  **distintos**; no se admite que fotos y comprobantes compartan ubicación.
- **Comprobantes privados**: modo `0700` en POSIX (ACL equivalente en Windows),
  archivos `0600` y sin exposición por rutas públicas del frontend.
- Sin enlaces simbólicos ni rutas relativas.
- Persistentes entre reinicios: no usar directorios temporales ni ubicaciones
  dentro del proyecto.

La preparación paso a paso, las rutas de ejemplo y la utilidad de preparación
de almacenamiento se documentan en **T-S7-01.2**
([PR #111](https://github.com/Sannlehnert/ferrepatagonia-industrial/pull/111)).
Cuando ese PR se integre en `develop`, la guía quedará en
`docs/sprint7/T-S7-01.2-usuarios-y-almacenamiento-local.md`. Esta guía no
duplica ese procedimiento.

## 5. Inicializar una base vacía

> **Detenerse si la base ya tiene tablas o datos.** `database/schema.sql` no es
> idempotente y no debe ejecutarse sobre un volumen persistente ya cargado.
> Esta comprobación es obligatoria antes de cualquier comando SQL.

Inspeccionar la identidad y el contenido actual (una sola línea, válida en Bash
y PowerShell):

```bash
docker compose exec mariadb mariadb --default-character-set=utf8mb4 -uferrepatagonia -pferrepatagonia_dev_only ferrepatagonia_dev -e "SELECT DATABASE(), VERSION(); SHOW TABLES;"
```

- Si no hay tablas, es una base nueva y se puede inicializar.
- Si ya existen las **24 tablas** y los **7 triggers** (3 FER-20 + 4 FER-17)
  y la vista `FER17_AUDITORIA_TRIGGERS`, la base está inicializada: no repetir los scripts.
- Si existen tablas pero faltan tablas o triggers, el volumen es anterior al
  esquema vigente. **No ejecutar `schema.sql`, no borrar el volumen y no usar
  `docker compose down -v`.** Respaldar y acordar con el equipo el procedimiento
  de actualización correspondiente.

Sobre una base nueva y vacía, ejecutar los scripts en este orden:

```bash
docker compose exec -T mariadb sh -c 'mariadb --default-character-set=utf8mb4 -uferrepatagonia -pferrepatagonia_dev_only ferrepatagonia_dev < /scripts/schema.sql'
docker compose exec -T mariadb sh -c 'mariadb --default-character-set=utf8mb4 -uferrepatagonia -pferrepatagonia_dev_only ferrepatagonia_dev < /scripts/migrate-fer-20-account-movements.sql'
docker compose exec -T mariadb sh -c 'mariadb --default-character-set=utf8mb4 -uferrepatagonia -pferrepatagonia_dev_only ferrepatagonia_dev < /scripts/migrate-fer-17-price-verification.sql'
docker compose exec -T mariadb sh -c 'mariadb --default-character-set=utf8mb4 -uferrepatagonia -pferrepatagonia_dev_only ferrepatagonia_dev < /scripts/migrate-s7-09-1-credit-workflow.sql'
```

`database/schema.sql` crea las 24 tablas base, pero **no incluye los triggers**.
`database/migrate-fer-20-account-movements.sql` instala las guardias y los tres
triggers obligatorios de cuenta corriente:

- `fer260_cuenta_revision` (`BEFORE UPDATE` en `CUENTA_CORRIENTE`);
- `fer260_imputacion_insert` (`BEFORE INSERT` en `IMPUTACION_MOVIMIENTO_CUENTA`);
- `fer260_imputacion_update` (`BEFORE UPDATE` en `IMPUTACION_MOVIMIENTO_CUENTA`).

`database/migrate-fer-17-price-verification.sql` instala la auditoría append-only
de precios y sus cuatro triggers, además de la vista de metadatos
`FER17_AUDITORIA_TRIGGERS`:

- `fer17_producto_alta_evento` (`AFTER INSERT` en `PRODUCTO`);
- `fer17_producto_precio_evento` (`AFTER UPDATE` en `PRODUCTO`).
- `fer17_precio_evento_no_update` y `fer17_precio_evento_no_delete` protegen el historial ante UPDATE y DELETE.

Ambas migraciones son idempotentes y pueden reaplicarse sin duplicar triggers.
No es necesario cargar `database/seed.sql` para considerar operativa la
infraestructura. En esta tarea el catálogo debe quedar vacío; no cargar los 904
SKU de DEMO ni los 100 productos definitivos de la tarea siguiente.

### Verificar tablas y triggers

Comando en una sola línea, válido en Bash y PowerShell:

```bash
docker compose exec mariadb mariadb --default-character-set=utf8mb4 -uferrepatagonia -pferrepatagonia_dev_only ferrepatagonia_dev -e "SELECT COUNT(*) AS tablas FROM information_schema.TABLES WHERE TABLE_SCHEMA = DATABASE() AND TABLE_TYPE = 'BASE TABLE'; SELECT TRIGGER_NAME, EVENT_MANIPULATION, ACTION_TIMING, EVENT_OBJECT_TABLE FROM information_schema.TRIGGERS WHERE TRIGGER_SCHEMA = DATABASE() ORDER BY TRIGGER_NAME; SELECT TABLE_NAME FROM information_schema.VIEWS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'FER17_AUDITORIA_TRIGGERS';"
```

Resultado esperado: **24 tablas** y exactamente los siete triggers indicados
(`fer17_precio_evento_no_delete`, `fer17_precio_evento_no_update`,
`fer17_producto_alta_evento`, `fer17_producto_precio_evento`,
`fer260_cuenta_revision`, `fer260_imputacion_insert`,
`fer260_imputacion_update`), además de la vista `FER17_AUDITORIA_TRIGGERS`.
Si el inventario es distinto, no continuar con el
arranque: revisar el estado de la base y la salida de los scripts.

### Validación opcional en una instancia descartable

Si se necesita probar una inicialización destructiva sin tocar el volumen de
desarrollo, usar un contenedor propio con `--tmpfs` y un nombre inequívoco. No
reutilizar el volumen `ferrepatagonia-dev_mariadb_data` ni una base de otro
integrante. Al finalizar, eliminar únicamente ese contenedor descartable.

## 6. Arrancar el backend

Desde `backend/`, para que `dotenv` lea `backend/.env`:

```bash
cd backend
npm run dev
```

La API escucha en `http://localhost:3000`. Verificar la salud en Bash:

```bash
curl -i http://localhost:3000/api/health
```

En PowerShell, usar `curl.exe` para invocar el cliente real y no el alias
`Invoke-WebRequest`:

```powershell
curl.exe -i http://localhost:3000/api/health
```

Respuesta esperada, HTTP **200**:

```json
{
  "api": "ok",
  "database": "ok"
}
```

Si la base no responde, el endpoint devuelve HTTP **503** con
`{"api":"ok","database":"error"}`. En ese caso revisar `docker compose ps`,
los logs de MariaDB y los valores `DB_*` de `backend/.env`.

`/api/health` **no valida el almacenamiento**. Para probar fotos, comprobantes
o importaciones, configurar y verificar primero las rutas de la sección 4.1;
sin ellas esas operaciones responden HTTP 503/404 o no persisten.

También se puede validar el arranque compilado:

```bash
npm run type-check
npm run build
npm start
```

`npm start` ejecuta `node dist/server.js` y requiere el mismo `backend/.env`.

## 7. Arrancar el frontend

En otra terminal, desde `frontend/`:

```bash
cd frontend
npm run dev
```

Abrir `http://localhost:5173`. Vite reenvía `/api` a
`http://localhost:3000` mediante el proxy existente de `vite.config.ts`.

Verificar:

- La página principal y las rutas públicas responden sin errores de página.
- `http://localhost:5173/api/health` devuelve HTTP 200 y el mismo JSON.
- El catálogo vacío se muestra como estado vacío, no como error de
  infraestructura.
- Las rutas públicas básicas navegan correctamente: `/`, `/catalogo`,
  `/ayuda`, `/sobre-nosotros`, `/login` y `/registro`.
- La consulta anónima a `/api/auth/me` puede devolver HTTP 401; es el
  comportamiento esperado de una sesión no autenticada y no indica una falla
  de conexión.

No cargar productos para “probar” el frontend. Un catálogo vacío es un estado
válido de esta tarea.

## 8. Problemas habituales

### Docker no responde

- Iniciar Docker Desktop o el servicio Docker.
- En Windows con WSL, comprobar que la integración WSL está habilitada para la
  distribución usada. Si `docker info` falla con
  `dial unix /var/run/docker.sock`, la CLI de WSL no está conectada al daemon.
- Verificar `docker context ls` y `docker compose version`.

### El puerto 3307 está ocupado

```bash
docker compose ps
docker ps --filter publish=3307
```

Detener el contenedor anterior si ya no se usa. No cambiar el puerto sin
acordarlo con el equipo, porque `backend/.env`, la documentación y las pruebas
asumen `3307`.

### El puerto 3000 o 5173 está ocupado

En Linux/WSL:

```bash
ss -ltnp | grep -E ':(3000|3307|5173)'
```

En PowerShell:

```powershell
Get-NetTCPConnection -LocalPort 3000,3307,5173 -ErrorAction SilentlyContinue
```

Si Vite elige otro puerto, el origen configurado en `APP_PUBLIC_ORIGIN` deja de
coincidir. Liberar `5173` o actualizar el origen y reiniciar el backend antes de
probar operaciones privadas.

### Health 503 o error de configuración

- Confirmar que MariaDB está `healthy`.
- Confirmar que `backend/.env` existe y que `DB_HOST`, `DB_PORT`, `DB_NAME`,
  `DB_USER` y `DB_PASSWORD` coinciden con `compose.yml`.
- Confirmar que `JWT_SECRET` no está vacío.
- Confirmar que `NODE_ENV=development` y
  `APP_PUBLIC_ORIGIN=http://localhost:5173`.
- Ejecutar el backend desde `backend/`, no desde la raíz: `dotenv` busca
  `.env` en el directorio de trabajo.

### `git status` muestra cientos de archivos modificados sin cambios reales

En Windows/OneDrive puede ocurrir por diferencias CRLF/LF. Comprobar sin
modificar nada:

```bash
git diff --ignore-cr-at-eol --stat
```

Si el resultado está vacío, no hay cambios de contenido. No commitear ese ruido
de fin de línea ni descartar trabajo local sin revisarlo antes.

## 9. Persistencia y comandos destructivos

- `docker compose stop mariadb` detiene el contenedor y **conserva** los datos.
- `docker compose down` elimina el contenedor y la red, pero **conserva** el
  volumen.
- `docker compose down -v` **elimina el volumen y todos los datos locales**.
- `docker volume prune` puede eliminar volúmenes no usados, incluidos datos de
  otros entornos locales.
- `DROP DATABASE`, `DROP TABLE` y `schema.sql` sobre una base cargada son
  operaciones destructivas.
- El volumen de MariaDB **no cubre** fotos, comprobantes ni importaciones: sus
  rutas deben ser persistentes, absolutas y externas al repositorio
  (sección 4.1). Un respaldo de la base sin esos directorios queda incompleto.
- Borrar o mover esos directorios deja registros de la base sin archivo
  asociado y estados de importación irrecuperables.
- No ejecutar ninguno de estos comandos sobre el volumen compartido sin
  respaldo verificado y autorización del equipo.
- No modificar ni eliminar los datos del entorno DEMO anterior.

## 10. Checklist de cierre

- [ ] `docker compose config` sin errores.
- [ ] MariaDB `healthy` en `127.0.0.1:3307`.
- [ ] `backend/.env` local creado, con `JWT_SECRET` no vacío y sin versionar.
- [ ] Base nueva con **24 tablas**, **7 triggers** (3 FER-20 + 4 FER-17) y la vista `FER17_AUDITORIA_TRIGGERS`.
- [ ] `npm --prefix backend run type-check` y `build` sin errores.
- [ ] `npm --prefix frontend run type-check` y `build` sin errores.
- [ ] `GET /api/health` devuelve HTTP 200 con `api` y `database` en `ok`.
- [ ] Si se probarán fotos, comprobantes o importaciones, las tres rutas de la
      sección 4.1 están configuradas, son absolutas, externas al repositorio y
      persistentes. Sin ellas, esas operaciones responden 503/404 o no
      persisten.
- [ ] `http://localhost:5173` abre y el proxy `/api` funciona.
- [ ] El catálogo vacío se muestra como estado vacío.
- [ ] Ningún secreto, `.env`, `node_modules`, `dist` ni archivo generado quedó
      versionado.

## Verificación de referencia

La guía se validó localmente el **15/11/2026** con Node 24.21.0, npm 11.19.0,
Docker 29.9.3, Docker Compose v5.7.0 y MariaDB 11.4.13. La referencia de CI
sigue siendo Node 22.22.2/npm 10.9.7.

Resultados obtenidos:

- `docker compose config` correcto; MariaDB existente `healthy`.
- Base nueva aislada: 21 tablas y los 3 triggers FER-20 en la corrida histórica
  de esta guía (antes de T-S7-05.2). Con la extensión vigente el esquema limpio
  tiene **24 tablas y 7 triggers**; la migración FER-20 se reaplicó sin duplicar
  triggers.
- Backend: `type-check` y `build` correctos; `npm start` y `npm run dev`
  respondieron HTTP 200 en `/api/health`.
- Frontend: `type-check` y `build` correctos; Vite respondió en `5173` y el
  proxy devolvió HTTP 200.
- Navegación pública verificada en navegador: `/`, `/catalogo`, `/ayuda`,
  `/sobre-nosotros`, `/login` y `/registro` sin errores de página ni de red.
  La única respuesta 401 observada fue `/api/auth/me`, esperada sin sesión.
- Catálogo y categorías vacíos devolvieron HTTP 200 con listas vacías.
- Pruebas: backend unitarias 1265/1265; frontend 221/221; migración FER-20
  8/8 en contenedor descartable.

En el equipo de verificación local existía un volumen persistente previo con 14
tablas y datos de desarrollo. **No se modificó**: la verificación limpia se
realizó en una base/instancia aislada, y la guía exige inspeccionar el contenido
antes de aplicar `schema.sql`.

Esta verificación de T-S7-01.1 **no configuró ni validó** los directorios de
almacenamiento (`PRODUCT_IMAGE_STORAGE_DIR`, `RECEIPT_STORAGE_DIR`,
`IMPORT_STORAGE_DIR`). Esas funciones se cubren en T-S7-01.2; no se deduce de
`/api/health` que fotos o comprobantes estén operativos.
