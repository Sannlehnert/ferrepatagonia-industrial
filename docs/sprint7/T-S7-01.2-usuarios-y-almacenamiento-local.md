# Sprint 7 · Usuarios locales de prueba y almacenamiento persistente (T-S7-01.2)

Esta guía complementa la instalación local normal (T-S7-01.1), incorporada en
el [PR #110](https://github.com/Sannlehnert/ferrepatagonia-industrial/pull/110)
(integrado en `develop`). Si tu rama todavía no incluye ese merge, los comandos
de esta página siguen siendo válidos: no dependen del archivo de la guía
T-S7-01.1, solo de la base con el esquema vigente y de `backend/.env`.

Explica cómo preparar **cuentas de prueba que realmente permiten iniciar sesión**
y cómo configurar **almacenamiento local persistente** para fotos de productos,
comprobantes e importaciones, sin usar el entorno `demo286-*`.

No reemplaza las guías canónicas: [Base de datos](../../database/README.md),
[Backend](../../backend/README.md) y
[Operación y liberación](../operaciones-release.md).

## 1. Qué resuelve esta tarea

`database/seed.sql` carga usuarios con hashes ficticios `TEST_ONLY_SHA256`:
son fixtures deliberados que **no permiten iniciar sesión** con bcrypt. Para
trabajar con sesiones reales en desarrollo existe un bootstrap local que crea
cuatro cuentas nuevas con contraseñas reales, sin debilitar la autenticación ni
tocar los fixtures existentes.

Además, los tres directorios de almacenamiento (`PRODUCT_IMAGE_STORAGE_DIR`,
`RECEIPT_STORAGE_DIR`, `IMPORT_STORAGE_DIR`) deben existir antes de usar los
endpoints que los necesitan y quedar fuera del checkout de Git. Una utilidad
local los prepara y verifica.

Ambos procedimientos son scripts locales de desarrollo: **no hay endpoints
HTTP** para preparar usuarios ni directorios, y no se modifica el registro
público ni la seguridad de producción.

> **Dependencia conocida (PR #109).** `develop` todavía no incorpora el hotfix
> que sí está en `main` para comprobantes bajo `npm run dev` y para el
> tratamiento HTTP de errores de imágenes. Este PR #111 **no copia ni
> reimplementa** ese hotfix. Hasta que se integre un PR separado de
> sincronización `main → develop`, esas dos limitaciones siguen vigentes en
> `develop`; no se corrigen desde esta tarea.

## 2. Preparar cuentas de prueba

### Requisitos previos

- Instalación local normal completada (T-S7-01.1, PR #110): base con **24 tablas**, **siete triggers** (3 FER-20 y 4 FER-17), la vista
  `FER17_AUDITORIA_TRIGGERS` y `backend/.env` con `NODE_ENV=development`.
- El script exige `NODE_ENV=development`; con `test` o `production` se rechaza
  sin hacer nada.
- Ejecutarlo **desde `backend/`**, que es donde `dotenv` busca `backend/.env`.

### Identificación obligatoria de la base

Antes de escribir, el script verifica los nombres de las tablas, los siete
triggers (incluidas sus tablas y operaciones) y la vista de auditoría. Si la base
es parcial o anterior, aborta sin modificar nada e indica que se necesita una
actualización controlada acordada con el equipo. **Nunca forzarla**: no ejecutar
`schema.sql`, `DROP DATABASE` ni `docker compose down -v` sobre ella.

### Ejecución

Desde la raíz del repositorio, entrar a `backend/` y ejecutar:

```bash
cd backend
node scripts/prepare-local-users.cjs           # inspección sin mutaciones
node scripts/prepare-local-users.cjs --apply   # aplica con confirmación explícita
```

Los mismos comandos en PowerShell (Windows):

```powershell
cd backend
node scripts/prepare-local-users.cjs
node scripts/prepare-local-users.cjs --apply
```

Para apuntar a otra base (por ejemplo una instancia aislada de prueba), los
valores del entorno tienen prioridad sobre `backend/.env`.

Bash:

```bash
NODE_ENV=development DB_HOST=127.0.0.1 DB_PORT=3308 \
DB_NAME=base_aislada DB_USER=root DB_PASSWORD='...' \
node scripts/prepare-local-users.cjs --apply
```

PowerShell:

```powershell
$env:NODE_ENV = "development"
$env:DB_HOST = "127.0.0.1"
$env:DB_PORT = "3308"
$env:DB_NAME = "base_aislada"
$env:DB_USER = "root"
$env:DB_PASSWORD = "..."
node scripts/prepare-local-users.cjs --apply
```

### Perfiles creados

| Clave       | Email                      | Rol     | Tipo       | Aprobación | Crédito |
|-------------|----------------------------|---------|------------|------------|---------|
| `admin`     | `admin.local@s7.test`      | ADMIN   | —          | —          | —       |
| `particular`| `particular.local@s7.test` | CLIENTE | PARTICULAR | —          | —       |
| `pendiente` | `pendiente.local@s7.test`  | CLIENTE | EMPRESA    | PENDIENTE  | ninguno |
| `aprobada`  | `aprobada.local@s7.test`   | CLIENTE | EMPRESA    | APROBADA   | ninguno |

- Los correos pertenecen al dominio ficticio `.test` y son distintos de los de
  `seed.sql` (`example.test`), que nunca se modifican.
- Cada cuenta recibe una **contraseña aleatoria individual** (bcrypt, costo 12,
  igual que el registro público). Nunca se imprime en consola ni en logs.
- Cada `EMPRESA` crea su fila `CLIENTE` y su `USUARIO` en una transacción con
  consultas parametrizadas. El `ADMIN` no tiene cliente asociado.
- **No se crea cuenta corriente, crédito ni movimientos contables.** La empresa
  aprobada arranca sin crédito: habilitarlo es una decisión administrativa que
  pertenece a otra tarea del Sprint 7.

### Credenciales privadas

Las contraseñas se escriben en un único archivo por base, **fuera del
repositorio**:

```text
~/.ferrepatagonia-local/test-users-<nombre-base>.json
```

En POSIX el directorio queda con permisos `0700` y el archivo `0600`; en
Windows la protección efectiva depende de las ACL del perfil de usuario (ver
la sección de almacenamiento). Para consultarlas de forma privada:

```bash
cat ~/.ferrepatagonia-local/test-users-ferrepatagonia_dev.json
```

```powershell
Get-Content "$HOME\.ferrepatagonia-local\test-users-ferrepatagonia_dev.json"
```

Ese archivo no se commitea, no se pega en PRs ni en documentación. Si la
computadora se comparte, bórralo después de usarlo. La ubicación puede
cambiarse con la variable `FERREPATAGONIA_LOCAL_DIR` (ruta absoluta).

La escritura usa un archivo temporal dentro del mismo directorio, `fsync` y
`rename` atómico cuando el filesystem lo permite. Un fallo de escritura se
informa explícitamente y **no se presenta como una transacción revertida**.

### Reejecución, recreación y concurrencia

El script es idempotente:

- Si el email ya tiene `USUARIO`, lo **omite** y no cambia su contraseña, rol,
  estado ni fecha.
- Si existe un `CLIENTE` con el email pero sin `USUARIO`, **bloquea** esa
  cuenta y pide revisión manual (no duplica clientes).
- Si no hay nada por crear, lo informa y **no reescribe** el archivo de
  credenciales: las contraseñas existentes se conservan.

**Recrear una base limpia conservando el mismo `DB_NAME`** es un caso
soportado: las cuentas realmente insertadas en esa ejecución reciben
contraseñas nuevas y sus entradas del JSON se **reemplazan** por las nuevas.
Las cuentas preexistentes que el script omitió (por ejemplo, en una base
parcial) conservan su credencial anterior: el bootstrap nunca restablece
contraseñas de usuarios existentes.

Dos ejecuciones simultáneas sobre una base vacía se serializan con un bloqueo
cooperativo `GET_LOCK` de MariaDB, identificado por `DB_NAME`. El bloqueo cubre
planificación, `INSERT`, `COMMIT` y escritura del archivo privado. El segundo
proceso espera hasta 30 segundos; si el primero no termina, aborta sin mutar
nada. El bloqueo se libera al terminar y MariaDB lo libera también si la
conexión se corta. Esto evita duplicados no controlados, pero **no es un
mecanismo distribuido** para clientes que no usen este mismo script.

Si el bootstrap detecta usuarios existentes pero **falta el archivo privado**
(o le faltan entradas), emite una advertencia y **no restablece contraseñas
automáticamente**. Para recuperar el acceso:

1. Lo más seguro es usar una base desechable nueva y volver a ejecutar el
   bootstrap.
2. Si la base debe conservarse, pedir a un administrador que restablezca la
   cuenta por el procedimiento administrativo correspondiente.
3. No borrar usuarios ni editar hashes a mano para “hacer que el JSON coincida”.

### Recuperación ante fallos del bootstrap

| Momento del fallo | Estado real | Acción recomendada |
|-------------------|-------------|--------------------|
| Antes del `COMMIT` | La transacción no se confirma; se intenta revertir. No hay usuarios parciales. | Corregir la causa y reintentar. |
| `COMMIT` falla o se corta la conexión | El estado es **incierto**. | Verificar la base antes de reintentar; el script lo informa así. |
| Después del `COMMIT`, al escribir credenciales | Los usuarios **persisten**, pero las contraseñas generadas no quedaron guardadas. | No reintentar sobre esa base esperando recuperarlas: usar una base desechable nueva o restablecer las cuentas manualmente. |
| Bloqueo ocupado más de 30 s | No se modificó nada. | Esperar a que termine el otro bootstrap y reintentar. |

Para empezar de cero en una base de prueba desechable, eliminar la base
completa (contenedor desechable), nunca solo las filas.

## 3. Permisos de cada perfil

Verificados contra `/api/auth/me` y rutas reales:

| Perfil               | `/api/auth/me` (rol / tipo)                  | Rutas administrativas | Cuenta corriente |
|----------------------|----------------------------------------------|-----------------------|------------------|
| `admin`              | `ADMIN` / `null` (nombre "Administrador")    | permitidas (200)      | —                |
| `particular`         | `CLIENTE` / `PARTICULAR`                     | prohibidas (403)      | `SIN_CUENTA`     |
| `pendiente` (EMPRESA)| `CLIENTE` / `EMPRESA`                        | prohibidas (403)      | `SIN_CUENTA`     |
| `aprobada` (EMPRESA) | `CLIENTE` / `EMPRESA`                        | prohibidas (403)      | `SIN_CUENTA`     |

- `SIN_CUENTA` es el estado del resumen cuando no existe `CUENTA_CORRIENTE`
  para el cliente: **sin límite, sin habilitación y sin movimientos**.
- El cierre de sesión (`POST /api/auth/logout`) borra la cookie `HttpOnly`.
  El JWT es sin estado: la invalidación efectiva es del lado del cliente, según
  el contrato vigente de autenticación.
- Tras reiniciar el backend las cuentas siguen disponibles (persisten en la
  base). Si se regenera `JWT_SECRET`, las sesiones abiertas se invalidan pero
  las contraseñas siguen siendo válidas.

## 4. Configurar almacenamiento persistente

### Variables y reglas

| Variable                   | Contenido                                   | Requisitos |
|----------------------------|---------------------------------------------|------------|
| `PRODUCT_IMAGE_STORAGE_DIR`| fotos de productos normalizadas (`.webp`)   | ruta absoluta, fuera del checkout, independiente de los otros dos |
| `RECEIPT_STORAGE_DIR`      | comprobantes de pago (privados)             | ruta absoluta, **fuera del checkout**, independiente, permisos privados (sin bits para grupo/otros en POSIX) |
| `IMPORT_STORAGE_DIR`       | estado de confirmación de importaciones     | ruta absoluta, independiente; si se omite, el servicio usa temporal **solo dev/test** (no persistente) |

Reglas que aplican los servicios existentes y que la utilidad verifica:

1. Rutas absolutas, sin NUL ni espacios en los extremos (validación Joi de
   `storage-env.config.ts`).
2. Deben existir antes de utilizarse. Si faltan, el backend puede arrancar y
   responder `/api/health`, pero los **endpoints que usan ese almacenamiento**
   responden con el error controlado correspondiente (503), en vez de crear el
   directorio o caerse.
3. Fuera del checkout de Git (la ruta de comprobantes, además, no puede
   contenerlo ni estar contenida en él).
4. **Los tres directorios son independientes entre sí, por pares.** No pueden
   ser iguales, ni contener a otro, ni estar contenidos en otro. Esto incluye
   `IMPORT` dentro de `RECEIPT`, `RECEIPT` dentro de `IMPORT`, y cualquier
   combinación con fotos de productos.
5. Ningún componente de la ruta puede ser un enlace simbólico o junction,
   **incluidos los directorios ancestrales**. La utilidad rechaza la ruta antes
   de crear nada.
6. Los archivos conservan su contenido al reiniciar los procesos.
7. Los comprobantes no son accesibles por rutas públicas del frontend: solo
   `/api/cuenta-corriente/comprobantes`, `/api/pedidos/:id/comprobantes` y
   `/api/admin/comprobantes` con sesión autorizada.
8. Se rechazan rutas y enlaces inválidos; **no hay fallback silencioso** a
   almacenamiento temporal para datos que deban persistir.

### Permisos POSIX y Windows

- En POSIX la utilidad crea los tres directorios con `0700`. No relaja un
  `0700` preexistente a `0755`; acepta permisos más restrictivos si siguen
  siendo operativos (lectura, escritura y acceso efectivos).
- Los comprobantes deben quedar sin permisos para grupo u otros. Si el
  directorio existente es más amplio, se corrige a `0700`.
- Si faltan permisos efectivos de lectura/escritura/acceso, la utilidad lo
  informa y, en POSIX, intenta corregirlos antes de usarlos.
- En **Windows** `chmod` no equivale a una ACL NTFS: solo cambia el atributo de
  solo lectura. La utilidad verifica el tipo de objeto y el acceso efectivo que
  Node puede comprobar, pero **no puede garantizar** el aislamiento de una ACL.
  Para comprobantes, revisar la carpeta con `icacls` y restringirla al usuario
  que ejecuta el backend. No se debe asumir que el script replica la protección
  POSIX `0700`.

### Ejecución

Desde la raíz del repositorio:

```bash
cd backend
node scripts/prepare-local-storage.cjs           # inspección sin mutaciones
node scripts/prepare-local-storage.cjs --apply   # valida TODO y recién después crea/corrige
```

```powershell
cd backend
node scripts/prepare-local-storage.cjs
node scripts/prepare-local-storage.cjs --apply
```

- La inspección informa el estado de cada variable:
  `OK`, `CREAR`, `CORREGIR`, `FALTA`, `INVALIDA` o `ERROR`.
- `--apply` **primero valida las tres variables, las rutas y los permisos**. Si
  una sola configuración es inválida, no crea ni modifica **ningún** directorio.
- Si todas son aplicables, crea las que falten (modo `0700`) y corrige permisos
  demasiado amplios o no operativos. **Nunca modifica `backend/.env`**.
- La operación **no es atómica** entre los tres directorios. Si el filesystem
  falla a mitad de camino, el script informa qué pudo haberse modificado y pide
  verificación manual; no promete una reversión que el filesystem no ofrece.
- Si falta o es inválida alguna variable, sugiere rutas por defecto bajo
  `~/ferrepatagonia-datos/` para copiar en `backend/.env`:

```dotenv
PRODUCT_IMAGE_STORAGE_DIR=/home/TU-USUARIO/ferrepatagonia-datos/fotos-productos
RECEIPT_STORAGE_DIR=/home/TU-USUARIO/ferrepatagonia-datos/comprobantes
IMPORT_STORAGE_DIR=/home/TU-USUARIO/ferrepatagonia-datos/importaciones
```

En Windows el equivalente es
`C:\Users\TU-USUARIO\ferrepatagonia-datos\...`. Usá siempre la ruta real de tu
equipo; no copies rutas de otra persona ni las versiones en archivos del repo.

### Dónde quedan los archivos

- `PRODUCT_IMAGE_STORAGE_DIR`: `<nombre-uuid>.webp`, servidos por la ruta
  pública `/api/product-images/:name`.
- `RECEIPT_STORAGE_DIR`: `<uuid>.pdf|jpg|png`, archivos `0600`, descarga solo
  autorizada.
- `IMPORT_STORAGE_DIR`: `<token>.json` con el estado de cada lote de
  importación; persistente mientras la variable esté definida.

## 5. Verificar después de un reinicio

1. `node scripts/prepare-local-storage.cjs` (desde `backend/`) debe reportar
   todo `OK`.
2. `curl -i http://localhost:3000/api/health` → 200
   `{"api":"ok","database":"ok"}`.
3. Iniciar sesión con una cuenta del bootstrap y verificar `/api/auth/me`.
4. Si había una imagen cargada, `GET /api/product-images/<nombre>.webp`
   sigue respondiendo 200.
5. `IMPORT_STORAGE_DIR`: los `<token>.json` siguen presentes y legibles.

## 6. Detectar configuraciones incorrectas

| Síntoma | Causa probable |
|---------|----------------|
| `FALTA` en la utilidad | variable sin definir en `backend/.env` |
| `INVALIDA: ruta absoluta...` | ruta relativa, con espacios en extremos o NUL |
| `INVALIDA: dentro... del checkout` | directorio configurado dentro del repo |
| `INVALIDA: enlace simbolico o junction` | enlace en el directorio final **o en un ancestro**; usar una ruta real |
| `INVALIDA: ... se solapa con ...` | dos de los tres almacenamientos son iguales o se contienen |
| `CORREGIR: permisos` | permisos demasiado amplios (p. ej. comprobantes `0755`) o sin acceso efectivo |
| `ERROR: configuracion incompleta o invalida; no se creo ni modifico...` | `--apply` abortó antes de mutar por una variable inválida |
| 503 `PRODUCT_IMAGE_REJECTED` / `COMPROBANTES_NO_DISPONIBLES` | se llamó a un endpoint que usa un directorio inexistente, sin permisos o fuera de política; no implica que el servidor no haya arrancado |
| `ERROR: ... no tiene el esquema vigente` | base anterior (p. ej. 14 tablas): no escribir; acordar sustitución controlada |
| `ADVERTENCIA: ... no tienen credencial ...` | usuarios existentes sin archivo privado o sin esa entrada; no se restablecen contraseñas solas |
| `ERROR: la transaccion ya fue confirmada...` | fallo al guardar credenciales después del `COMMIT`; los usuarios persisten y las contraseñas no se guardaron |

## 7. Acciones prohibidas sobre bases existentes

- `DROP DATABASE`, `DROP TABLE`, `TRUNCATE` y `schema.sql` sobre una base con
  datos.
- `docker compose down -v` y `docker volume prune` (pueden borrar el volumen de
  desarrollo o de otros entornos).
- Reejecutar `seed.sql` sobre tablas cargadas (el propio script lo rechaza).
- Modificar los 904 productos del entorno DEMO ni cargar el catálogo definitivo
  de 100 productos en esta tarea.
- Ejecutar el bootstrap con `NODE_ENV` distinto de `development`.
- Sobrescribir contraseñas o estados de cuentas existentes: el bootstrap nunca
  actualiza filas, solo crea y actualiza las credenciales de lo que creó.
- Copiar el hotfix del PR #109 dentro de este PR: la sincronización
  `main → develop` debe resolverse en un PR separado.
