## 1. Objetivo, alcance y definiciones

Este documento ordena la verificación de los flujos de negocio y seguridad del
Sprint 7, separa la cobertura ya existente de la que falta, y propone un orden de
ejecución reproducible con los comandos y perfiles que existen en el repositorio.

### 1.1 Qué cubre

- Catálogo público, búsqueda, filtros, paginación, detalle y ordenamiento.
- Registro de clientes `PARTICULAR` y `EMPRESA`.
- Autenticación, restauración de sesión, logout, roles y sesiones cruzadas.
- Precios FER-17, listas propias, evidencia USD y verificación administrativa.
- Carrito, stock y persistencia.
- Pedidos a cuenta corriente, cotización, idempotencia, historial y concurrencia.
- Crédito comercial: solicitud, aprobación, rechazo, habilitación, límite y baja.
- Comprobantes de pago y revisión documental. **No existe pasarela de pago online**;
  “pagos” en este plan significa comprobantes y su revisión, sin acreditar saldos.
- Mi Cuenta y consulta de cuenta corriente.
- Operaciones ADMIN: productos, stock, imágenes, importación, categorías, listas
  de precios, clientes/empresas, pedidos, comprobantes y crédito.
- Persistencia tras reinicio de MariaDB y de procesos.
- Escenarios de 401/403, IDOR, sesiones cruzadas, reintentos, concurrencia,
  estados comerciales y fallos de infraestructura.

### 1.2 Qué no cubre

- Implementar las pantallas o endpoints faltantes.
- Certificar el entorno desplegado, TLS/proxy real, respaldos o capacidad de
  producción.
- Aprobar datos `DEMO` o precios sintéticos como datos comerciales reales.
- Ejecutar pruebas destructivas sobre una base persistente compartida.

### 2.3 Dependencias y riesgos de integración

1. **#115 y #117 comparten precios.** Ambos modifican repositorios/servicios de
   precios y pruebas de catálogo/ADMIN. Se debe definir el orden de merge y
   repetir la suite de precios después de cada fusión, no asumir que un CI verde
   aislado sigue siendo válido tras resolver conflictos.
2. **#115 y #118 cambian el esquema.** #115 agrega `FER17_PRECIO_EVENTO` y dos
   triggers FER-17; #118 agrega dos tablas de crédito. El orden documentado por
   #118 deja 24 tablas y 5 triggers. Cualquier verificación de instalación limpia
   debe comprobar el inventario exacto, no un conteo fijo aislado.
3. **#116 depende de que la cuenta y el crédito sean distinguibles.** Sin #118,
   la UI puede mostrar aprobación/cuenta, pero no existe flujo de solicitud de
   crédito. Sin #116, `develop` no expone el estado comercial separado.
4. **#119 no tiene UI.** No se puede aprobar un escenario de navegador de
   ordenamiento hasta que exista un control habilitado y conectado al parámetro
   `orden`.
5. **#329 no tiene UI.** El plan no debe declarar “crédito cubierto en navegador”:
   la cobertura disponible y propuesta es API/MariaDB. La interfaz queda como
   brecha y tarea siguiente.
6. **Los perfiles de producción no son equivalentes al perfil de CI.** Los
   hallazgos H01, H02 y H03 de #284 siguen abiertos; el plan los incluye como
   dependencia y no como cobertura aprobada.

5. **Seguridad de endpoints nuevos.** Falta una matriz consolidada 401/403/IDOR

8. **Journey transversal de precios.** No hay una prueba única que recorra

### 11.2 Estados permitidos

| Estado | Significado |
| --- | --- |
| **No ejecutado** | No hay corrida en el commit candidato. No se aprueba. |
| **Aprobado** | Se ejecutó y pasó con evidencia adjunta. |
| **Fallido** | Se ejecutó y falló; requiere corrección o riesgo aceptado. |
| **Bloqueado** | No se puede ejecutar por una dependencia (PR, UI, dato, entorno). |
| **No aplica** | Se justifica por alcance; no cuenta como cobertura. |

Este documento deja **todas** las pruebas en “No ejecutado” salvo las que se
citan como evidencia histórica de otro commit, que no se reutilizan como
aprobación de Sprint 7.

  aprobados, o un bloqueo explícito con responsable y fecha. Ningún 401/403/IDOR
  abierto; ningún efecto financiero parcial; evidencia adjunta.

  Sprint. Un P1 fallido no puede presentarse como P0 aprobado.
- **P2:** planificados y ejecutados si el tiempo lo permite; no bloquean por sí

## Anexo C. Consultas SQL de verificación (solo lectura)

Usar solo en la base descartable o en una copia aislada. No ejecutar `UPDATE`,
`DELETE`, `DROP`, `TRUNCATE` ni migraciones como parte de una verificación de
lectura.

```sql
-- Pedido y cargo
SELECT id_pedido, estado, modalidad_pago, subtotal, descuento, total, moneda_total
FROM PEDIDO WHERE id_pedido = ?;

SELECT tipo_movimiento, origen, id_pedido, monto, moneda, estado
FROM MOVIMIENTO_CUENTA_CORRIENTE WHERE id_pedido = ?;

-- Evidencia de precio vigente
SELECT id_producto, precio, stock, activo FROM PRODUCTO WHERE id_producto = ?;
SELECT precio_verificado, evidencia, valida, sintetica, verificado_utc
FROM PRECIO_USD_EVIDENCIA WHERE id_producto = ?;

-- Esquema y triggers (instalación limpia)
SELECT COUNT(*) AS tablas FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE();
SELECT TRIGGER_NAME, EVENT_MANIPULATION, ACTION_TIMING, EVENT_OBJECT_TABLE
FROM information_schema.TRIGGERS
WHERE TRIGGER_SCHEMA = DATABASE() ORDER BY TRIGGER_NAME;
```
